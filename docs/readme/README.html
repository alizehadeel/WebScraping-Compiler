DSL for Static Web Scraping: Compiler

Compiler Construction project: Phase 1 interpreter (Flex + Bison) and Phase 2 ahead-of-time compiler to LLVM IR. Runs on Linux.

Quick start on Ubuntu 24.04 (about 5 minutes)

sudo apt update
sudo apt install -y build-essential flex bison libxml2-dev clang llvm
cd WebScraping-Compiler           # the project folder
make                              # builds the compiler ./dslc
make test                         # runs every test (both phases)

cd examples
../dslc prices.dsl --run          # Phase 1: interpret the program
../aot.sh prices.dsl              # Phase 2: compile to a native executable ./prices
./prices
Both commands print 4 and write cheap_prices.txt. On Ubuntu 22.04 the LLVM version must be changed: see section 2.

1. What the project is

The project implements a small programming language for extracting data from saved (static) HTML pages: a program opens a local .html file, grabs the text of every element that matches a CSS selector (as text or as numbers), processes it with ordinary variables, loops, conditions, arrays (rows) and functions (recipes), and prints or saves the result. The language is also complete enough to write general algorithms such as Insertion Sort and Merge Sort.

One program, dslc, contains both phases of the assignment:

PhaseWhat it doesCommand
Phase 1: interpreterFlex scans the source, Bison parses it, and the program is executed directly. No intermediate code is produced../dslc prog.dsl --run
Phase 2: AOT compilerThe same Flex/Bison front end, but the program is translated into LLVM IR (.ll). The IR is optimized with LLVM opt and compiled into a native executable with clang../dslc prog.dsl -o prog.ll
or in one step:
./aot.sh prog.dsl

For the same program, both phases produce the same output. The test suite checks this for every test program.

3. Compiling the program

From the project folder:

make            # builds ./dslc (the compiler and interpreter)
make clean      # removes ./dslc and the build/ folder

make runs Bison on src/parser.y and Flex on src/lexer.l (into build/), compiles every C++ file in src/ and the C runtime runtime/rt.c, and links them with libxml2 into the executable ./dslc. Bison runs with -Werror -Wcounterexamples, so the grammar builds with zero conflicts and the whole build has no warnings.

$ make
bison -Wall -Wcounterexamples -Werror -d -o build/parser.tab.cpp src/parser.y
flex -o build/lexer.yy.cpp src/lexer.l
g++ -std=c++17 -Wall -Wextra -g ... -c -o build/ast.o src/ast.cpp
...
g++ -std=c++17 -Wall -Wextra -g -o dslc build/ast.o ... build/rt.o -lxml2

If aot.sh or tests/run.sh report “Permission denied” (some zip tools drop the executable bit), run chmod +x aot.sh tests/run.sh.

4. Running the program

./dslc <file.dsl> (--run | -o <out.ll> | --check | --ast | --ast-opt)
CommandWhat it does
./dslc prog.dsl --runPhase 1. Parses, checks and interprets the program.
./dslc prog.dsl -o prog.llPhase 2. Parses, checks, optimizes and writes LLVM IR to prog.ll.
./aot.sh prog.dsl [-o exe]Phase 2 in one step: dslc -o, then opt -O2, then clang + runtime + libxml2. Builds a native executable (default name: prog, next to prog.dsl) and keeps prog.ll.
./dslc prog.dsl --checkParses and runs semantic analysis only (exit code 0 = program is correct).
./dslc prog.dsl --astPrints the abstract syntax tree built by the Bison parser.
./dslc prog.dsl --ast-optPrints the tree after constant folding and dead-code removal.
Run programs from the folder that holds their HTML files. File names in open and save are relative to the current directory, so for the examples use cd examples first and call ../dslc and ../aot.sh.

Phase 1: interpret

$ cd examples
$ ../dslc prices.dsl --run
4
$ cat cheap_prices.txt
-15
150
320
450

Phase 2: compile ahead of time, in one step

$ ../aot.sh prices.dsl
built prices (LLVM IR in prices.ll)
$ ./prices
4

Phase 2: the same steps by hand

../dslc prices.dsl -o prices.ll                  # 1. front end + LLVM IR generation
llvm-as prices.ll -o /dev/null                   # 2. (optional) check that the IR is valid
opt -O2 -S prices.ll -o prices.opt.ll            # 3. middle-end: optimize the IR
clang -Wno-override-module prices.opt.ll ../runtime/rt.c -I../runtime \
      $(xml2-config --cflags --libs) -o prices   # 4. back end: native code + runtime + libxml2
./prices                                         # 5. run

Any middle-end that reads and writes textual LLVM IR can replace step 3 (for example opt -passes=mem2reg -S, which is what the test runner uses by default). aot.sh honours OPT, CLANG and MIDDLE_END_FLAGS environment variables, for example OPT=opt-15 CLANG=clang-15 ./aot.sh prog.dsl.

What the generated IR looks like

For show 2 + 3 * 4, the AST optimizer folds the constant before IR generation:

$ echo 'show 2 + 3 * 4' > a.dsl && ./dslc a.dsl -o a.ll && tail -5 a.ll
define i32 @main() {
entry:
  call void @rt_show_num(i64 14)
  ret i32 0
}

A recursive recipe (from tests/ok/recursion.dsl) becomes an ordinary LLVM function:

define i64 @dsl_fact(i64 %arg.n) {
entry:
  %v1.n = alloca i64
  store i64 %arg.n, ptr %v1.n
  %t1 = load i64, ptr %v1.n
  %t2 = icmp sle i64 %t1, 1
  %t3 = zext i1 %t2 to i64
  %t4 = icmp ne i64 %t3, 0
  br i1 %t4, label %if.then.1, label %if.end.2
if.then.1:
  ret i64 1
if.end.2:
  %t5 = load i64, ptr %v1.n
  %t6 = load i64, ptr %v1.n
  %t7 = sub i64 %t6, 1
  %t8 = call i64 @dsl_fact(i64 %t7)
  %t9 = mul i64 %t5, %t8
  ret i64 %t9
}

5. Running the tests

make test

This runs three test suites:

  1. Runtime self-test (build/test_rt): opens both example pages and checks the runtime functions (selectors, grab, number conversion, rows).
  2. Phase 1 (tests/run.sh --run): every program in tests/ok/ is interpreted and its output compared with the .out file; every program in tests/err/ must fail with the expected line number and message; every program in tests/opt/ must give the expected optimized AST.
  3. Phase 2 (tests/run.sh --compile): every program in tests/ok/ is compiled to LLVM IR, checked with llvm-as, optimized with opt, linked with clang, run, and its output compared with the same .out file. This step is skipped with a message if clang/llvm-as are not installed.
Expected result
all runtime checks passed (0 failures)
./tests/run.sh --run
all passed: 75 passed, 0 skipped (mode --run)
all passed: 26 compiled and matched, 0 skipped (mode --compile)

Other ways to run the tests: tests/run.sh --check, tests/run.sh --ast, and with a different middle-end: MIDDLE_END="opt -O2 -S" tests/run.sh --compile.

6. Using the language

Source files use the extension .dsl. A program is a sequence of recipe (function) definitions and top-level statements in any order. The top-level statements are the main program and run from top to bottom.

Lines, blocks, comments

  • One statement per line; the end of the line ends the statement (no semicolons).
  • A block opens with >> at the end of a line and closes with << on its own line. else goes on the closing line: << else >> or << else if cond >>.
  • # starts a comment to the end of the line. Blank lines are ignored.

Types

TypeValues
num64-bit signed integer. Arithmetic wraps on overflow. Comparisons and logic give 1 (true) or 0 (false); any non-zero value is true.
textImmutable string: "..." with escapes \", \\, \n. Only == and != apply.
row num, row textFixed-size array indexed from 0, made by row num of n / row text of n (filled with 0 or "") or by grab. Rows are references (passing one to a recipe does not copy it). count(r) gives the size.

Statements

SyntaxMeaning
hold x <- exprDeclare a variable; its type is the type of expr and never changes.
x <- expr   r[i] <- exprAssign to a variable / a row element (same type required).
if c >> ... << else >> ... <<Condition; else and else if are optional.
while c >> ... <<Loop while c is non-zero.
for i from a until b >> ... <<i = a, a+1, …, b-1 (b excluded). Bounds are evaluated once. i is read-only.
recipe f(num a, row text t) -> num >> ... <<Define a recipe. -> type is optional. Recursion is allowed; recipes can be called before they are defined.
give expr   giveReturn from a recipe (with or without a value). Without a give, a recipe returns 0, "" or an empty row.
f(x, y)Call a recipe as a statement.
open "page.html"Read and parse a local HTML file; it becomes the current page.
show exprPrint a value and a newline (a row prints one element per line).
save expr to "file.txt"Write a value to a file, replacing it (a row: one element per line).

Expressions (lowest to highest precedence)

OperatorsNotes
orShort-circuit: the right side runs only if the left is 0.
andShort-circuit: the right side runs only if the left is non-zero.
not1 if the operand is 0, else 0.
== != < <= > >=Not chainable. ==/!= take two nums or two texts; the rest take nums.
+ -num only.
* / %num only; / truncates toward zero; dividing by zero is a run-time error.
unary -num only.

Primary expressions: numbers, texts, variables, r[i], recipe calls, ( expr ), count(r), row num of n, row text of n, and grab.

Extracting data: grab

  • grab "selector" → a row text with the text of every matching element of the current page, in document order, trimmed, with inner whitespace collapsed to one space.
  • grab "selector" as num → a row num. Each element's text gives its first integer, ignoring commas between digits and dropping any fraction: "Rs. 1,299.50" → 1299, "-15" → -15. Text with no digits is a run-time error.
  • Supported selectors: tag, .class, #id, tag.class, tag#id, and these separated by spaces for descendants (div.product span.price). The compiler rejects anything else, for example div > p or a[href].
  • open and grab are only allowed in the main program, and every grab must come after an open in the same or an enclosing block (checked at compile time).

The full language definition and grammar (EBNF) are in docs/Compiler_Project_Proposal_revised.docx.

7.1 Prices: extract, sort, filter, save (examples/prices.dsl)

shop.html contains six products with prices such as Rs. 1,299.50, Rs. 450 and -15. The program grabs them as numbers, sorts them with the msort/merge recipes (Merge Sort, shown in 7.4), keeps the ones under 500, saves them, and prints how many there are.

open "shop.html"
hold prices <- grab "span.price" as num
hold n <- count(prices)
hold tmp <- row num of n
msort(prices, tmp, 0, n - 1)
# prices are now ascending, so the cheap ones come first
hold k <- 0
while k < n and prices[k] < 500 >>
    k <- k + 1
<<
hold cheap <- row num of k
for i from 0 until k >>
    cheap[i] <- prices[i]
<<
save cheap to "cheap_prices.txt"
show k
Run (both phases print the same)
$ ../dslc prices.dsl --run

$ cat cheap_prices.txt

450
$ ../aot.sh prices.dsl && ./prices

recipe isort(row num r, num n) >>
    for i from 1 until n >>
        hold key <- r[i]

            r[j + 1] <- r[j]

    <<

7.4 Merge Sort with recursion (examples/msort.dsl)

recipe merge(row num a, row num tmp, num lo, num mid, num hi) >>
    hold i <- lo
    hold j <- mid + 1
    hold k <- lo
    while i <= mid and j <= hi >>
        if a[i] <= a[j] >>
            tmp[k] <- a[i]
            i <- i + 1
        << else >>
            tmp[k] <- a[j]
            j <- j + 1
        <<
        k <- k + 1
    <<
    while i <= mid >>
        tmp[k] <- a[i]
        i <- i + 1
        k <- k + 1
    <<
    while j <= hi >>
        tmp[k] <- a[j]
        j <- j + 1
        k <- k + 1
    <<
    for t from lo until hi + 1 >>
        a[t] <- tmp[t]
    <<
<<

recipe msort(row num a, row num tmp, num lo, num hi) >>
    if lo < hi >>
        hold mid <- (lo + hi) / 2
        msort(a, tmp, lo, mid)
        msort(a, tmp, mid + 1, hi)
        merge(a, tmp, lo, mid, hi)
    <<
<<

9. How the compiler works

             prog.dsl
                │
   Flex  ─────► lexer.l      tokens + line numbers (NL token ends each statement)
   Bison ─────► parser.y     grammar actions build the syntax tree (ast.h)
                │
           sema.cpp          2 passes: recipe signatures, then scopes, types and all checks
                │
     ┌──────────┴──────────────┐
     │ --run   (Phase 1)       │ -o   (Phase 2)
 interp.cpp                 opt.cpp          constant folding, code after give removed
 executes the tree          codegen.cpp      LLVM IR text: expressions, control flow, @main
 directly                   codegen_recipes.cpp  recipes, calls, give, rows, count
     │                           │
     │                      prog.ll ─► opt (middle-end) ─► clang ─► native executable
     │                           │
     └──── runtime/rt.c (open, grab, show, save, bounds/zero checks; uses libxml2) ────┘
  • Phase 1, Flex and Bison: the scanner and parser are generated only by Flex and Bison. The Bison grammar actions build a syntax tree, which the interpreter executes directly. No intermediate code (IR, bytecode) is produced on this path. A tree is needed because loops and recipe calls must run statements many times, but Bison actions run only once, while the file is being read.
  • Phase 2, AOT: the same Bison front end feeds the IR generator. The generated .ll file is plain textual LLVM IR (opaque pointers), so the standard LLVM tools can optimize it and compile it into an executable.
  • Values: num = i64; text = pointer to a C string; rows = pointer to %Row = type { i64 len, i64 is_text, ptr data }. Every variable is an alloca (promoted to registers by opt). Row access calls rt_check_index first.
  • Same behaviour in both phases: both use the same runtime library and the same order of evaluation, so the compiled program always prints what the interpreter prints. make test checks this.

11. Troubleshooting
